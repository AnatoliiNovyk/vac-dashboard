# Крок 4: Рефакторинг джерела даних для Manager View

**Дата:** 27.05.2024

## Мета

Усунути серйозну архітектурну вразливість, за якої клієнтський додаток менеджера завантажував усі періоди відпусток з бази даних і фільтрував їх локально. Замінити цей підхід на безпечний, цільовий запит до Firestore, що повертає дані тільки для команди конкретного менеджера.

## Зміни

### Рефакторинг `app.js`

1.  **Асинхронний рендеринг:**
    - Функції `applyFilters`, `getVacationPeriodsForCurrentTab`, `switchTab`, `updateUIForTab`, та `rerenderUI` були перетворені на `async` функції, щоб коректно обробляти прямі запити до бази даних.

2.  **Оптимізація початкового завантаження даних:**
    - Під час ініціалізації програми (`initializeApp`) глобальний список `appData.vacation_periods` тепер завантажується **тільки** якщо поточний користувач має роль `hr`. Для всіх інших ролей (менеджер, співробітник) цей список на старті залишається порожнім, що зменшує початкове навантаження.

3.  **Цільовий запит для менеджерів:**
    - **[КЛЮЧОВА ЗМІНА]** У функції `getVacationPeriodsForCurrentTab` логіка для вкладки `manager-team` була повністю переписана.
    - **Стара логіка (небезпечна):** Фільтрація глобального масиву `appData.vacation_periods`.
    - **Нова логіка (безпечна):** Виконується прямий запит до Firestore:
        ```javascript
        const subordinateIds = appData.employees.filter(e => e.manager_id === appState.currentUser.id).map(e => e.id);
        const managerTeamQuery = await db.collection('vacation_periods').where('employee_id', 'in', subordinateIds).get();
        return managerTeamQuery.docs.map(doc => ({ id: doc.id, ...doc.data() }));
        ```
    - Цей підхід гарантує, що на клієнт менеджера потрапляють **тільки** дані про відпустки його прямих підлеглих.

4.  **Цільові запити для інших ролей:**
    - Аналогічно, для вкладки `my-view` у не-HR користувачів тепер також виконується цільовий запит `db.collection('vacation_periods').where('employee_id', '==', appState.currentUser.id).get()`, щоб отримати лише власні відпустки.

## Вплив на систему

- **Підвищена безпека:** Повністю усунено ризик, коли менеджер міг потенційно отримати доступ до даних про відпустки співробітників не з його команди.
- **Дотримання принципу мінімізації даних:** Додаток тепер запитує з бекенду тільки ті дані, які необхідні для виконання поточного завдання.
- **Покращена продуктивність:** Для менеджерів та співробітників значно зменшено обсяг даних, що передаються при завантаженні та оновленні, що позитивно впливає на швидкість роботи.
- **Підготовка до ієрархії:** Хоча поточна реалізація працює для прямих підлеглих, вона створює правильний патерн для майбутнього вдосконалення (наприклад, через Cloud Function) для підтримки повної ієрархії менеджменту.
